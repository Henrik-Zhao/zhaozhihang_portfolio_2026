/ 项目背景

安全运营的问题，不只是“信息太多”。

当资产、漏洞、检测结果、工单与报告分散在不同页面时，用户真正缺失的是一条可确认、可执行、可追溯的决策链。

这个项目的目标不是再做一个数据大屏，而是把风险治理的核心对象和状态串起来：用户可以从一项互联网暴露资产进入风险证据，发起 Agent 研判，确认处置方案，生成工单，并在复测后把结果回写到报告。

当前展示为交互原型；任务运行与数据回写用于演示，不连接真实生产系统。

/ 核心判断

用户不需要更多孤立的告警，
而需要知道：先处理什么、为什么、谁来做，以及下一步会发生什么。

/ 01 定义问题

用三个产品问题，收拢复杂需求。

我把页面级需求重新组织为对象、优先级和闭环三类问题。它们既决定信息架构，也决定后续的交互验证重点。

01

看不清全局

资产、风险和工单各有统计，但用户无法快速理解它们之间的关系与当前压力。

02

排不出优先级

风险等级不足以支持处置，还需要结合外部暴露、业务重要度、证据可信度和 SLA。

03

闭不了环

研判结论如果不能进入工单、复测和报告，就只是一次性的分析结果。

/ 02 组织系统

让信息架构围绕业务对象生长。

导航没有照搬组织分工，而是沿着治理对象展开。任何详情都能看到来源、关联对象、当前状态和可执行动作。

/ 03 建立优先级

从“风险列表”转向“处置队列”。

列表保留专业信息密度，同时把严重等级、影响资产、状态、责任人和 SLA 放到同一视线内。用户可以在扫描过程中直接进入研判或建单。

/ 04 引入 AI，但保留控制权

Agent 不是一个“生成答案”按钮。

工作台把任务拆成目标理解、数据获取、证据判断、方案比较和写回审批。每一步都有状态与来源，冲突数据不会被悄悄忽略，任何生产写操作都停在人工确认之前。

  • 范围可见任务目标、资产范围与数据截止时间始终可核对。
  • 证据可追研判结论关联风险、资产、工单与工具执行记录。
  • 动作可控创建或修改工单前展示变更预览，并要求人工审批。

/ 05 系统设计

让复杂界面保持一致，而不是变得空。

企业后台需要高信息密度。设计重点不是盲目留白，而是通过统一容器、间距和状态语义，降低每次阅读的重新学习成本。

/ 交付结果

从页面集合，推进到可演示的产品闭环。

13个可访问产品路由
8个核心业务页面
2类完整 Agent 任务

以下为原型交付范围，不代表真实业务收益或生产系统能力；本次视觉整理未新增用户测试。

最终原型支持浏览器前进/后退、抽屉与弹窗焦点管理、批量操作反馈、失败重试、状态回写和移动端适配。它不仅能展示视觉方案，也能用于评审关键流程与产品边界。

/ 下一步

原型验证了“怎么工作”，下一步需要验证“是否更好地工作”。

后续应接入真实数据权限，验证风险排序规则，并围绕安全运营人员、业务负责人和管理层分别开展任务型可用性测试。

对 Agent 场景，还需要持续观察证据可信度、人工接管率和建议被采纳后的处置结果。
