鉴微平台子专题 · 高保真交互原型

/ 设计命题

企业 AI 的价值，不是替用户跳过判断。

重大漏洞处置同时涉及威胁情报、资产版本、互联网暴露、业务归属和已有工单。Agent 可以加速信息汇总，但错误写回会直接放大风险。

因此，产品把 Agent 定义为“受控的任务执行者”：它先解释计划，再逐步展示来源与冲突，生成可比较的方案，最后将写操作停在人工审批队列中。

当前展示为交互原型；任务运行与数据回写用于演示，不连接真实生产系统。
场景
Fastjson 重大漏洞应急处置
设计目标
24 小时内完成影响研判与分批计划
关键约束
可读生产数据，写操作需审批
输出
影响资产、证据、方案与工单草稿

/ 核心原则

好的 Agent UX 不只解释“答案是什么”，
还要让用户知道：它做了什么、依据什么、接下来会改动什么。

/ 01 任务先于对话

用执行计划建立共同预期。

自由输入适合表达意图，但高风险任务不能只留下一个聊天记录。工作台先把目标、范围、时限和输出结构化，再生成五步执行计划。

  1. 01
    理解目标与冻结范围

    确认漏洞、环境、资产范围、时限和已有工单。

  2. 02
    汇聚情报与关联对象

    连接威胁情报、组件清单、资产台账和业务关系。

  3. 03
    验证影响与证据

    区分已确认、可能受影响、已排除和数据不足。

  4. 04
    生成分批处置方案

    比较风险下降、业务影响、缓解措施与升级计划。

  5. 05
    预览并审批写回

    展示工单变更，获批后才更新业务对象。

/ 02 证据不是附件

把“为什么”放在结论发生的地方。

风险详情将版本、暴露面、扫描证据和业务关系集中到一个可下钻的上下文中。发生数据冲突时，界面明确标记“待人工确认”，而不是用一个看似确定的答案覆盖差异。

/ 03 把控制权设计进流程

每个写操作，都有一道看得见的门。

Agent 可以读取风险、资产、组件和工单；不能自动修改生产对象。审批页逐项列出要更新的工单、要新建的任务、关联对象和字段变化，用户可以取消单项动作，再统一提交。

READ

查询默认开放

数据源、时间和工具运行记录全程保留。

WRITE

写入必须预览

新增、更新与发布动作展示具体字段变化。

APPROVE

审批后再回写

审批人、时间、来源任务进入审计记录。

/ 04 让结果继续流动

Agent 输出不是终点。

审批后的处置计划会写入工单；整改反馈推动风险进入待复测；复测通过后，风险和资产计数同步更新；报告再引用这些已验证对象。

研判结论→工单草稿→整改反馈→复测闭环→报告引用

/ 05 从分析到报告

同一套可信机制，也用于内容生成。

智能报告先冻结数据范围，再生成分析与章节草稿。每个结论关联引用对象；局部数据失败时保留可用结果，并支持只重试失败部分。

/ 产品结果

一套可被检查的 Agent 体验，而不是一个不可见的黑箱。

5步重大漏洞研判计划
7个智能报告章节草稿
3类写操作审批动作

以下为原型交付范围，不代表真实业务收益或生产系统能力；本次视觉整理未新增用户测试。

完整原型覆盖任务创建、计划确认、运行进度、证据与冲突、方案比较、失败恢复、人工审批、数据回写和审计披露，可用于产品评审和任务型可用性测试。

/ 产品反思

信任不是一句“AI 生成”，而是每一个可核对的小决定。

当场景风险越高，越不能把解释性压缩成一段总结。范围、来源、冲突、权限和审批都应该成为产品的一等对象。

后续验证重点应包括：用户在何时接管任务、哪些证据最能支持判断，以及建议被接受后是否真正缩短处置时间。
